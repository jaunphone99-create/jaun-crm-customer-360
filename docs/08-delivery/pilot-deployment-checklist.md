### 3.6 ตั้งตัวแปรสภาพแวดล้อมของเว็บ และด่านกัน driver ปลอม

`web/src/lib/env.ts` เป็นที่เดียวที่แอปอ่านตัวแปรสภาพแวดล้อม และมี **ด่านกันสองชั้น** ที่ต้องเข้าใจก่อนตั้งค่า:

| ด่าน | อ่านจากโค้ด | ผลที่เกิด |
|---|---|---|
| `JCRM_ENV` ต้องเป็น `dev` · `staging` · `prod` | ตรวจตอน import | ค่าอื่น = โยน error ตั้งแต่บูต |
| `JCRM_DB_DRIVER` ต้องเป็น `supabase` หรือ `dev` | ตรวจตอน import | ค่าอื่น = โยน error ตั้งแต่บูต |
| `assertDriverSafe()` — `JCRM_DB_DRIVER=dev` ใช้ได้เฉพาะ `JCRM_ENV=dev` | ตรวจตอน **ใช้งานจริงครั้งแรก** ไม่ใช่ตอน import | หลุดขึ้น staging/prod = **คำขอแรกล้มทันที** พร้อมข้อความชัดเจน |
| `assertDriverSafe()` — `JCRM_DB_DRIVER=dev` ใช้กับ `NODE_ENV=production` ไม่ได้ | เหมือนข้างบน | กันฐานทดลองหลุดขึ้นของจริง |

## 7. ขั้นที่ 5 — นำเข้าข้อมูลเดิม

**ผลลัพธ์ที่ต้องได้:** พนักงานค้นเจอลูกค้าเดิมตั้งแต่วันแรกของ Pilot · คุณภาพข้อมูลอยู่ในเกณฑ์

> Runbook เต็ม M0–M5: `data-migration-plan.md` §9 · เกณฑ์รับ: §10 · mapping: §4 · ค่าช่องทางติดต่อ: §5 · ข้อมูลซ้ำ: §6 · batch และ `app.bulk`: §8

### 7.1 จังหวะที่ถูกต้อง — นำเข้าก่อนหรือหลัง UAT

**คำตอบ: แยกเป็นสองท่อน — เตรียมและซ้อมก่อน UAT · ลงจริงบน prod หลัง UAT ผ่าน และก่อนวันเปิด Pilot**

| ท่อน | ทำที่ไหน | เมื่อไร | เหตุผล |
|---|---|---|---|
| **5A** — M0 เตรียม · M1 Dry run · M2 รายงานตรวจสอบ | **staging** | **ก่อนหรือขนานกับ UAT** | ต้องรู้ให้เร็วที่สุดว่าข้อมูลต้นทางคุณภาพพอหรือไม่ · ถ้าไม่พอจะได้กลับไปทำความสะอาดที่ต้นทางทัน (ความเสี่ยง R5 · roadmap §9) |
| **5B** — M3 Cut-over · M4 Verification | **prod** | **หลัง UAT ตัดสิน Go · ก่อนวันเริ่ม Pilot** | เหตุผลสามข้อด้านล่าง |

**ทำไม cut-over ต้องอยู่หลัง UAT ไม่ใช่ก่อน**

1. **UAT ไม่ได้ทำบน prod อยู่แล้ว** — `test-cases-uat.md` §4.2 ระบุชัดว่า UAT ทำบน **staging ด้วย `seed.sql`** และ **"ห้ามทำ UAT บน prod"** · การนำเข้าลงจริงจึงไม่ได้ช่วยให้ UAT ทำได้เร็วขึ้นแม้แต่น้อย
2. **ถ้า UAT เจอข้อบกพร่อง S1/S2 ที่ต้องแก้ด้วย migration** การมีข้อมูลลูกค้าจริงอยู่บน prod แล้วทำให้การแก้แพงขึ้นและเสี่ยงขึ้นทันที
3. **หน้าต่างถอยกลับของการนำเข้าแคบมาก** — `data-migration-plan.md` §9.5 และ roadmap §6.4 L4 ระบุตรงกันว่า การถอยข้อมูลที่นำเข้าทำได้สะอาด **เฉพาะก่อนมีกิจกรรมจริงผูกกับแถวที่นำเข้า** · ยิ่งข้อมูลอยู่บน prod นานก่อนเปิดใช้ ความเสี่ยงยิ่งไม่ได้ลดลง แต่โอกาสพลาดเพิ่มขึ้น

**ข้อจำกัดที่ต้องไม่ลืม:** `data-migration-plan.md` §9.2 (หมายเหตุ M10) ห้ามรัน dry run ด้วย **ไฟล์จริง** บน environment ที่ไม่ใช่ prod โดยไม่ผ่านการพิจารณาของ DPO — เพราะไฟล์ต้นทางคือข้อมูลจริงเช่นกัน

> **[รอยืนยัน]** เจ้าของโครงการสั่งลำดับไว้เป็น "5 นำเข้า → 6 UAT" · การแยกเป็น 5A/5B ข้างบนคือการตีความว่าท่อนไหนอยู่ตรงไหนของลำดับนั้น **ต้องได้รับการยืนยันก่อนลงมือ**

## 10. Full Smoke Test บน environment ของ Pilot

> **คำสั่งของเจ้าของโครงการ (CANONICAL ข้อ 20.19): ก่อนเปิดให้พนักงานจริง ต้องรัน Full Smoke Test บน environment ที่จะใช้ Pilot อีกครั้ง — ไม่ใช้ผลจาก local dev แทน**
> **เกณฑ์ผ่านที่ตรึงไว้: ผ่านทุกข้อ และไม่มีข้อที่ถูกข้าม**

### 10.1 ทำไมผล local dev ใช้แทนกันไม่ได้

หัวไฟล์ `tools/smoke-test.py` ระบุเหตุผลไว้แล้ว: สิ่งที่ต่างกันคือของจริงทั้งหมด — **ตัวตนผ่าน Supabase Auth จริง · RLS บนข้อมูลจริง · เครือข่ายของสาขา · และ HTTPS ที่หน้าจอ production เท่านั้นที่บังคับ**
สคริปต์ยิงผ่าน **HTTP ของแอปจริง ไม่ใช่ยิง RPC ตรง** เพราะสิ่งที่ต้องพิสูจน์คือ "ผู้ใช้เปิดหน้าแล้วได้ของจริง" ไม่ใช่ "ฐานข้อมูลตอบได้"

### 10.2 สร้างไฟล์ตั้งค่าของ environment

รูปแบบตามหัวไฟล์ `tools/smoke-test.py` — **คีย์ `web` · `api` · `accounts` ขาดไม่ได้** (สคริปต์จะออกพร้อมข้อความ `ไฟล์ตั้งค่าขาดคีย์ …`)

```json
{
  "label": "JAUN CRM · Pilot (prod)",
  "web":    "https://<โดเมนของ Pilot>",
  "api":    "https://<project-ref>.supabase.co/rest/v1/rpc",
  "apikey": "<publishable key ของ project นั้น>",
  "accounts": {
    "ST-0001": { "cookie": "sb-...-auth-token=...", "jwt": "eyJ..." },
    "ST-0002": { "cookie": "...", "jwt": "..." },
    "ST-0020": { "cookie": "...", "jwt": "..." },
    "ST-0045": { "cookie": "...", "jwt": "..." }
  }
}
```

**บัญชีที่สคริปต์เรียกใช้จริง** (อ่านจากตัวสคริปต์) — ต้องมีครบทั้งสี่ ไม่งั้นจะถูก "ข้าม":

| รหัสในสคริปต์ | บทบาทที่ต้องใช้ | ใช้ทดสอบอะไร |
|---|---|---|
| `ST-0001` | `EXECUTIVE` | หน้าหลัก · เทียบตัวเลขการ์ด/Funnel/โดนัท/เหตุผลที่ไม่สำเร็จ กับ `api.get_kpis` และ `api.get_dashboard_charts` |
| `ST-0002` | `BUSINESS_ADMIN` | ประวัติการใช้งานทั้งหกมุมมอง · ตรวจ PII บนหน้า 12 · 16 · 17 · 18 |
| `ST-0020` | `BRANCH_MANAGER` @ JP1 | หน้าหลักของผู้จัดการ · ยืนยันว่า**ไม่มีสิทธิ์**เปิดประวัติการใช้งาน |
| `ST-0045` | `STAFF` @ JP1 | รับลูกค้า (07) · Quick Capture (04) · รายการลูกค้า (03) · Customer 360 (05) · การปิดบังเบอร์ |

> **บัญชีบน Pilot ไม่ได้ชื่อ `ST-0001` เสมอไป** — รหัสเหล่านี้เป็นรหัสพนักงานในชุดข้อมูลตัวอย่าง (CANONICAL ข้อ 13.5)
> บน environment จริง ให้ใส่ **รหัสพนักงานจริงที่มีบทบาทตรงตามคอลัมน์กลาง** เป็นคีย์ใน `accounts` แทน
> **[รอยืนยัน]** ว่าจะจับคู่บัญชีจริงกับรหัสในสคริปต์อย่างไร (แก้สคริปต์ = แก้โค้ด ซึ่งอยู่นอกขอบเขตรอบนี้)

### 10.3 เอา cookie / jwt มาจากไหน

**บน environment จริงไม่มีทางปลอมตัวตนได้ และไม่ควรมี** — ผู้รันต้องเข้าสู่ระบบด้วยบัญชีจริงของแต่ละบทบาทก่อน แล้วคัดลอกเซสชันมา
ซึ่ง**พิสูจน์ไปในตัวว่าการเข้าสู่ระบบจริงใช้งานได้** ก่อนจะทดสอบอย่างอื่น

| ค่า | เอามาจากไหน | สคริปต์ใช้ทำอะไร |
|---|---|---|
| `cookie` | เข้าสู่ระบบบนเบราว์เซอร์จนถึงหน้าหลัก → เปิดเครื่องมือนักพัฒนา → คัดลอก cookie ของเซสชัน (ชื่อขึ้นต้น `sb-`) | ส่งเป็น header `Cookie` ตอนเปิดหน้าเว็บ — cookie เป็น **HttpOnly** จึงต้องคัดลอกจากแผง Application/Storage ไม่ใช่จาก `document.cookie` |
| `jwt` | access token ของเซสชันเดียวกัน (บัญชีที่บทบาทบังคับ MFA **ต้องยืนยัน TOTP แล้ว** เพื่อให้ได้ `aal2`) | ส่งเป็น `Authorization: Bearer <jwt>` ตอนเรียก RPC |
| `apikey` | Dashboard → Project Settings → API → publishable key | ส่งเป็น header `apikey` คู่กับ JWT (PostgREST ต้องการทั้งสอง) |

> JWT มีอายุ **900 วินาที (15 นาที)** ตามค่า A10 — ถ้ารันไม่ทันจะได้ข้อผิดพลาดกลางคัน ให้คัดลอกใหม่แล้วรันใหม่ อย่าลดค่า A10 เพื่อให้ทดสอบสะดวก

หัวไฟล์สคริปต์เขียนไว้ตรง ๆ: **ไฟล์ตั้งค่ามี token ของคนจริง = ความลับ**

## 12. แผนถอยกลับ (rollback)

**หลักที่ห้ามลืม: migration เป็น forward-only — ไม่มี "ถอย schema"** การแก้โครงสร้างที่ผิดทำด้วย migration ใหม่เสมอ (`deployment-backup-recovery.md` §3.3 กติกา M2)

| ระดับ | อาการ | ทำอะไร | ผลต่อข้อมูล | เอกสาร |

### 12.3 ถ้าต้องแตะ prod ด้วยมือ — Break-glass (§10)

ทุกอย่างต่อไปนี้ถือเป็น break-glass และต้องผ่าน §10.2 ทั้ง 5 ขั้น: **กู้คืน PITR บน prod · หมุน secret · เปลี่ยนสมาชิก/สิทธิ์ของ org · เปิด SQL editor หรือเชื่อมต่อฐานข้อมูล prod ด้วยมือ · เปลี่ยนการตั้งค่า Auth/Data API นอก release · ban/เพิกถอน session ด้วยมือ · ดูค่า service_role key**
