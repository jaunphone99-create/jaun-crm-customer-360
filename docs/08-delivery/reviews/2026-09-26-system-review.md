# ผลตรวจระบบ JAUN CRM — 26 กันยายน 2569

> อัปเดตหลังแก้ไขตามคำขอ: แก้ทั้ง 3 จุดด้านล่างแล้ว รายละเอียดเดิมเก็บไว้เป็นหลักฐานการตรวจ
> `dev:db` ใช้เวลาจริงโดยปริยาย (เลือก snapshot ได้ด้วย `--as-of`), `claimVisit` ตรวจจำนวนแถวที่อัปเดต,
> และ LINE ใช้ปุ่ม “แสดง LINE ID” พร้อมวัตถุประสงค์ audit แบบ VIEW
> รีสตาร์ตฐานเดิมแล้วและยืนยันในเบราว์เซอร์ว่ารายการวันที่ 26 กันยายนกลับมาอยู่ในคิววันนี้ โดยไม่ล้างข้อมูล
> หลังแก้ `check:web` รวม regression 4 กรณี, smoke test และ production build ผ่านทั้งหมด
> การทดสอบรับคิวซ้ำใช้ Server Action ตัวจริงกับขอบเขตฐานข้อมูลจำลอง ไม่ใช่การกดพร้อมกันจากพนักงานสองคน

ตรวจระบบ local development (Next.js + PGlite) จากโค้ด ชุดทดสอบที่มีอยู่ HTTP และหน้ารับลูกค้าในเบราว์เซอร์ ไม่ได้ทดสอบ Supabase Auth จริง การส่งอีเมล หรือ production และไม่ได้แก้โค้ดระบบหรือข้อมูลธุรกิจ

## ปัญหาที่พบ

### P1 — รายการรับลูกค้าใหม่ไม่ปรากฏในคิววันนี้ของโหมดทดลอง

- หน้ารับลูกค้าใช้ช่วงวันที่จาก `get_kpis(TODAY)` ซึ่งอิง `app.clock()`; seed ตรึงวันที่ไว้ที่ 11 กันยายน 2569 เวลา 10:24
- `api.open_visit` ใช้ `now()` เมื่อไม่มี `occurred_at` และ Server Action ไม่ส่งค่านี้
- ตรวจพบรายการ `V-JP3-260926-001` อยู่ในฐานข้อมูลจริงของเครื่องนี้ สถานะ `IN_SERVICE` เวลา `2026-09-26T16:11:29.268Z` แต่หน้ารับลูกค้า JP3 แสดงวันที่ 11 กันยายนและคิวเปิด 0 รายการ แม้มีข้อความเริ่มให้บริการสำเร็จ
- ผลกระทบ: พนักงานมองไม่เห็นรายการที่เพิ่งรับและทำงานต่อจากคิวไม่ได้
- ตำแหน่ง: `supabase/migrations/0011_api.sql:1694`, `web/src/features/reception/queries.ts:85`, `web/src/features/reception/actions.ts:74`
- แนวแก้: ให้สภาพแวดล้อมทดลองแบบรับรายการสดใช้เวลาเดียวกันทั้งรายงานและรายการใหม่ หรือแยกโหมดข้อมูลตัวอย่างที่ตรึงเวลาออกอย่างชัดเจน ต้องไม่เปลี่ยนนาฬิกาที่ใช้ตัดสินสิทธิ์และ audit โดยไม่พิจารณาข้อกำหนด

### P2 — รับคิวอาจรายงานสำเร็จทั้งที่ไม่ได้เปลี่ยนรายการ

- `claimVisit` อัปเดตเฉพาะแถวสถานะ `WAITING` แต่ตรวจเพียง `error` ไม่ตรวจว่ามีแถวถูกเปลี่ยนจริง
- หากพนักงานสองคนรับคิวเดียวกัน คนที่สองอาจอัปเดต 0 แถวและยังได้รับข้อความ “รับคิวแล้ว”
- พบจากการอ่านโค้ด ยังไม่ได้จำลองการกดพร้อมกันในเบราว์เซอร์
- ตำแหน่ง: `web/src/features/reception/actions.ts:34–43`
- แนวแก้: ขอแถวผลลัพธ์และยืนยันว่าเปลี่ยนได้หนึ่งรายการ หากไม่มีให้แจ้งว่าคิวถูกเปลี่ยนสถานะแล้ว พร้อมโหลดคิวล่าสุด

### P2 — ปุ่ม “เปิด LINE” ไม่เปิด LINE

- ปุ่มส่ง `LINE_OPEN` แต่ผลลัพธ์เข้าส่วนแสดง LINE ID บนหน้าจอ ไม่มีการเปิดแอปหรือลิงก์
- เป็นข้อจำกัดที่ระบุไว้ในคอมเมนต์ แต่ชื่อปุ่มยังทำให้ผู้ใช้คาดหวังอีกพฤติกรรมหนึ่ง
- พบจากการอ่านโค้ด ไม่ได้เรียกแอปภายนอก
- ตำแหน่ง: `web/src/features/customer360/ContactList.tsx:74`
- แนวแก้: เปลี่ยนชื่อปุ่มให้ตรงกับการแสดง ID หรือกำหนดและทดสอบรูปแบบลิงก์ก่อนเปิดใช้งาน

## ข้อจำกัดก่อนใช้งานจริง

- ระบบปัจจุบันเป็น dev login เลือกตัวตนได้โดยไม่ตรวจรหัสผ่าน จึงเป็นผลตรวจของสภาพแวดล้อมทดลองเท่านั้น
